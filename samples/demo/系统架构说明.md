# DocMind 系统架构说明

## 整体分层

系统采用 Ports and Adapters（六边形架构），业务核心不依赖具体中间件，
所有外部能力通过端口接口接入，实现可替换。

```
接入层    Controller（REST）  /  MCP Server  /  SSE 流式端点
  ↓
应用层    ChatService  IngestionService  RetrievalService  AdminService
  ↓
端口      CachePort  StoragePort  MessageBus  LockPort  KeywordSearchPort
  ↓
适配器    Redis / 内存    本地磁盘 / MinIO    Kafka / 内存总线   数据库锁
```

## 关键设计

### 1. 端口抽象带来的可替换性

| 端口 | 生产实现 | 开发实现 |
| --- | --- | --- |
| CachePort | RedisCacheAdapter | 内存 ConcurrentHashMap |
| StoragePort | MinioStorageAdapter | LocalStorageAdapter |
| MessageBus | KafkaMessageBus | InMemoryMessageBus |
| KeywordSearchPort | PostgreSQL 全文检索 | 数据库 ILIKE |

dev profile 下全部走内存或本地实现，因此零外部依赖即可启动完整功能。

### 2. 异步摄取流水线

文档上传后不阻塞 HTTP 响应，立即返回文档 ID，后续流程由消息总线驱动：

PENDING → PARSING → CHUNKING → EMBEDDING → INDEXED

每个阶段更新进度百分比，失败时按指数退避重试（默认 3 次），
重试耗尽后写入死信队列并在文档列表标记 FAILED。

### 3. 混合检索

单一向量检索在专有名词、型号、编号上表现不佳，
单一关键词检索又缺乏语义泛化能力。因此采用双通道 + RRF 融合：

- 向量通道：embedding 余弦相似度，权重 0.65
- 关键词通道：PostgreSQL tsvector 与 ILIKE 兜底，中文用 bigram 分词，权重 0.35
- 融合：RRF，公式中的 k 取 60，避免头部结果被单一通道垄断

### 4. 可观测性

Micrometer 埋点覆盖：文档摄取各阶段耗时、检索召回数与耗时、
首 token 延迟、token 消耗、配额命中次数。
MDC 中的 traceId 贯穿 HTTP 请求 → 线程池任务 → Kafka 消息，
任一环节日志都可通过同一 traceId 串起来。

### 5. 安全

JWT 无状态鉴权 + RBAC 两种角色（ADMIN / MEMBER）。
审计日志记录关键操作。配额与限流基于 Redis Lua 脚本实现原子计数。
MCP 端点独立鉴权并配合知识库白名单。
