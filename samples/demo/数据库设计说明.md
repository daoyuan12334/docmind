# DocMind 数据库设计说明

## 一、总体说明

生产环境使用 PostgreSQL 16 及以上，配合 pgvector 扩展做向量检索。
开发环境使用 H2 兼容模式，表结构一致，向量检索退化为内存实现。

命名规范：表名小写复数（`knowledge_bases`），字段下划线分隔（`created_at`），
时间统一存 UTC 并在展示层转本地时区。

## 二、核心表

### 2.1 knowledge_bases（知识库）
| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | bigserial PK | 知识库 ID |
| name | varchar(128) | 名称 |
| description | text | 描述 |
| visibility | varchar(16) | PRIVATE / PUBLIC |
| owner_id | bigint | 创建者 |
| document_count | int | 文档数（冗余，异步维护） |
| chunk_count | int | 切片数（冗余，异步维护） |
| created_at / updated_at | timestamptz | 创建 / 更新时间 |

索引：`idx_kb_owner`（owner_id）、`idx_kb_visibility`（visibility）。

### 2.2 documents（文档）
| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | bigserial PK | 文档 ID |
| kb_id | bigint FK | 所属知识库 |
| file_name | varchar(255) | 原始文件名 |
| content_type | varchar(128) | MIME 类型 |
| file_size | bigint | 字节大小 |
| checksum | varchar(64) | 内容 SHA-256，用于判重 |
| storage_key | varchar(512) | 对象存储键 |
| status | varchar(16) | PENDING/PARSING/CHUNKING/EMBEDDING/INDEXED/FAILED |
| progress | int | 0 至 100 |
| error_message | text | 失败原因 |
| retry_count | int | 已重试次数 |
| created_at / updated_at | timestamptz | 时间 |

唯一约束：`(kb_id, checksum)` —— 同一知识库内相同内容只允许存在一份。
索引：`idx_doc_kb_status`（kb_id, status）支撑列表筛选。

### 2.3 chunks（切片）
| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | bigserial PK | 切片 ID |
| document_id | bigint FK | 所属文档 |
| kb_id | bigint | 冗余，避免检索时回表 |
| chunk_index | int | 片内序号 |
| content | text | 切片正文 |
| token_count | int | token 估算值 |
| page_no | int | 页码（PDF / PPT） |
| slide_no | int | 幻灯片号（PPT） |
| sheet_name | varchar(128) | 工作表名（Excel） |
| embedding | vector(1536) | 向量，维度随模型配置 |

索引：
- `idx_chunk_doc`（document_id）
- `idx_chunk_kb`（kb_id）
- 向量索引：HNSW，`vector_cosine_ops`，`m=16`、`ef_construction=64`

> 注意：pgvector 的 HNSW 索引必须在有数据后建才高效；空表建索引再灌数据，
> 图结构质量差，召回率明显下降。因此脚本中的做法是**先灌数据后建索引**。

### 2.4 conversations / messages（会话与消息）
| 表 | 字段要点 |
| --- | --- |
| conversations | id、user_id、title、kb_ids（jsonb）、created_at、updated_at |
| messages | id、conversation_id、role（USER/ASSISTANT）、content、sources（jsonb）、created_at |

`sources` 以 jsonb 存引用数组，避免再开一张表。结构：
```json
[{ "index": 1, "documentId": 1234, "fileName": "产品手册.md", "chunkIndex": 3, "score": 0.82 }]
```

### 2.5 users（用户）
| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | bigserial PK | |
| username | varchar(64) UNIQUE | |
| password_hash | varchar(128) | BCrypt |
| role | varchar(16) | ADMIN / MEMBER |
| enabled | boolean | |
| quota_daily | int | 每日问答配额 |
| created_at | timestamptz | |

### 2.6 audit_logs（审计日志）
只增不改不删。字段：id、user_id、action、target_type、target_id、
detail（jsonb）、ip、user_agent、created_at。
按月分区，保留 24 个月。

## 三、向量维度配置

不同 embedding 模型维度不同，建表时须与配置一致：

| 模型 | 维度 | 备注 |
| --- | --- | --- |
| text-embedding-v3（通义） | 1024 | 默认 |
| text-embedding-3-small（OpenAI） | 1536 | |
| bge-large-zh | 1024 | 本地部署 |

**改模型即等于换维度**，必须重建 `chunks` 表或新增列后重新灌数据，
不能只改配置——老向量与新维度不匹配会直接报错。

## 四、数据一致性

1. `document_count` / `chunk_count` 是冗余字段，由摄取流水线的监听器在
   INDEXED / DELETED 事件后异步更新，允许短暂不一致，在列表页做最终一致展示
2. 删除文档时先删 chunks 再删 documents，顺序不可颠倒，否则外键报错
3. 删除知识库走事务：documents → chunks → knowledge_base，
   向量删除在事务提交后异步执行，失败进补偿任务

## 五、容量估算

| 项 | 估算 |
| --- | --- |
| 单文档平均切片数 | 文本 30 至 80 片；PPT 每页 1 片；PDF 每页 1 至 2 片 |
| 单切片平均 token | 300 |
| 1024 维向量存储 | 每片约 4KB（向量）+ 正文 |
| 10 万片规模 | 向量部分约 400MB，加正文与索引约 1.5GB |

建议 `chunks` 表在超过 50 万片时按 kb_id 做分区。
