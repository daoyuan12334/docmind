# 编码规范与代码评审清单

## 一、Java 编码规范

### 1.1 命名
- 类名 UpperCamelCase，方法名与变量名 lowerCamelCase，常量 UPPER_SNAKE_CASE
- 包名全小写，不使用下划线
- 布尔字段不要用 `is` 开头（避免 Jackson 序列化生成两个字段）
- 接口不要加 `I` 前缀，实现类不要加 `Impl` 之外的无意义后缀

### 1.2 方法
- 单方法不超过 80 行，超过就要拆
- 参数超过 4 个的，改为参数对象
- 不使用 `Map<String, Object>` 作为跨层传递结构，用例场景一律定义明确类型
- 返回值不要返回 `null`，集合返回空集合，对象用 `Optional` 或在方法名上体现（如 `findXxx`）

### 1.3 异常
- 业务异常统一继承 `BizException`，携带 `code` 与 `message`
- 禁止吞异常：catch 后必须记录日志或重新抛出，空 catch 块一律打回
- 禁止用异常做流程控制
- 日志中打印异常用 `log.error("描述 {}", param, e)`，不要 `e.getMessage()` 单独打印

### 1.4 并发
- 线程池必须自定义，禁止 `Executors.newFixedThreadPool`（无界队列会 OOM）
- 线程池必须命名（`ThreadFactory`），排查时靠名字定位
- 异步任务必须传 traceId，否则日志串不起来
- 分布式锁必须有过期时间，禁止无 TTL 的锁

## 二、Spring 相关

### 2.1 依赖注入
- 一律构造器注入，禁止字段 `@Autowired`
- 循环依赖视为设计问题，不允许用 `@Lazy` 绕过

### 2.2 事务
- `@Transactional` 标注在应用层服务方法，不标在 Controller
- 事务方法内禁止远程调用、禁止耗时 IO（模型调用一律放事务外）
- 只读查询加 `@Transactional(readOnly = true)`

### 2.3 配置
- 配置类用 `@ConfigurationProperties` + 明确前缀，禁止散落的 `@Value`
- 配置前缀必须项目专属（如 `docmind.`），避免与环境变量宽松绑定撞名
  > 教训：会话环境注入过 `SERVER__PORT`，被宽松绑定识别为 `server.port`，
  > 导致端口被劫持。专属前缀是唯一可靠的规避方式。
- 敏感配置一律走环境变量或密钥服务，禁止入库、禁止进仓库

### 2.4 分层职责
| 层 | 职责 | 禁止 |
| --- | --- | --- |
| Controller | 参数校验、鉴权、组装响应 | 写业务逻辑、直接调 Mapper |
| Application Service | 编排用例、事务边界 | 处理 HTTP 细节 |
| Domain | 业务规则 | 依赖框架注解 |
| Adapter | 对接中间件 | 泄漏实现细节到上层 |

## 三、前端规范（Vue 3）

- 组件用 `<script setup>`，选项式 API 不再用于新代码
- 组件文件名 PascalCase，单文件不超过 300 行
- 状态管理只用一处（本项目为局部 ref + 组合式函数），禁止又用 store 又用 provide/inject 传同一份数据
- 所有请求走统一的 axios 实例，禁止在组件里散落 `fetch`
- 请求拦截统一处理 401，组件内不重复写跳转逻辑
- 布局断点统一在 `<992px` 视为窄屏，不允许各页面自己定义断点

## 四、代码评审清单

### 4.1 正确性（阻塞项）
- [ ] 边界条件：空集合、null、零值、超长输入是否处理
- [ ] 并发安全：共享变量是否有竞态
- [ ] 异常路径：失败时状态是否回滚或标记，是否会留下脏数据
- [ ] 幂等性：重复调用（重试、用户连点）是否产生重复数据
- [ ] 事务边界：耗时操作是否在事务外

### 4.2 安全（阻塞项）
- [ ] 是否存在越权：资源是否校验了归属当前用户
- [ ] 密钥、口令、内网地址是否进代码或日志
- [ ] 用户输入是否做了长度与类型校验
- [ ] 上传文件是否校验了类型与大小

### 4.3 可观测性
- [ ] 关键路径是否有日志，日志是否带可检索的关键字（如文档 ID）
- [ ] 新接口是否纳入指标埋点
- [ ] 异步任务是否传了 traceId

### 4.4 可维护性
- [ ] 命名是否能让半年后的自己看懂
- [ ] 重复逻辑是否抽取
- [ ] 魔法数字是否定义为常量
- [ ] 新增配置是否在 `.env.example` 与 README 同步说明

### 4.5 测试
- [ ] 新增业务逻辑是否有单测
- [ ] 修复的缺陷是否有回归用例（且验证过"改回 bug 会变红"）
- [ ] 涉及协议解析的（SSE、MCP 等）是否按真实报文格式写了用例

## 五、评审流程

1. 提交前自检：跑通 `mvn test` 与 `npm test`，本地启服务冒烟
2. 至少 1 人评审通过方可合入，核心链路（鉴权、配额、摄取）需 2 人
3. 评审意见分为 `阻塞` / `建议` / `提问` 三类，只有阻塞项未解决才能否决
4. 评审不超过 24 小时响应，超时可由作者直接合入并留言

## 六、明确不要求的

- 不要求 100% 测试覆盖率：协议解析、金额计算、权限判定必须有，
  简单 getter / 配置类不强制
- 不要求统一注释风格：注释解释"为什么"，不要复述"做了什么"
- 不要求一次改到位：遗留代码允许"经过即改善"，不必专门开重构任务
